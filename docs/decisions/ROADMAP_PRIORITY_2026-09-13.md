# 路线优先级决策（2026-09-13）

状态：**已采纳**。

决策日期：2026-09-13。

取代：[路线优先级决策（2026-09-04）](ROADMAP_PRIORITY_2026-09-04.md)。

## 1. 决策目的与适用范围

本决策根据当前工程基础和团队目标，调整后续实施范围、顺序、分工及阶段门。

核心调整为：

- 取消 M4 CipherGPT 实施、适配及性能任务。
- 保留 M2、M3、M5 编号和历史验收记录。
- 先完成 Protocol I 精确三轮核心、通信核验和公共接口交接。
- 随后完成 Protocol III 精确两轮核心、通信核验及基础接口交接。
- 将 M6 拆为 M6A AAV86、M6B BB90+DCF。
- 每条升级路线均包含 Protocol I、Protocol III 两种实现及完整性能验收。
- M6A 完整验收后，再推进 M6B 的依赖实现和正式实验。
- M7 保留最终六种方案的横向汇总，不承担被推迟的全部升级性能测试。

本决策只调整实施路线，不改变已冻结的输入、稳定同分、rank、输出和统一指标语义，也不将未完成候选升级为已完成实现。

## 2. 决策依据

### 2.1 当前已有基础

- M1/M1.1 已完成统一语义、oracle、基础适配、metrics 和测试入口。
- M2 已完成 C 级 Protocol I 工程基线，核心四轮，raw-score 到原顺序 mask 共八轮。
- M2.16 完成精确核心可行性与泄露审计，没有新增 paper-exact 原语。
- M3 已在 `main@bb0d0e8` 完成三轮模块化核心及 raw-score 五轮扩展。
- 两条路线已具备可复用的比较、通信、材料、输入输出和独立进程测试基础。
- 论文精确核心、完整通信核验、自适应图预处理和正式升级性能实验仍需继续完成。

### 2.2 调整理由

1. 当前研究重点是 Agarwal Protocol I、Protocol III 及两种图算法升级。继续实施 CipherGPT 会增加独立运行时和适配工作，因此将其移出本轮范围。
2. Protocol I 精确核心先闭合公共功能与计量边界，便于 Protocol III 在明确接口上推进。
3. 在每个精确核心完成后立即核验通信，可以尽早发现遗漏阶段、位宽差异、封装开销或协议实现偏差。
4. 接口交接必须发生在实现和通信核验之后，避免下一阶段继承尚未解释的行为或计量假设。
5. AAV86 先完成两种路线及完整性能测试，形成可复用的图执行、材料和实验基础。
6. BB90+DCF 涉及顺序统计量、在线阈值、稳定同分及最终成员选择，应作为独立组合阶段实施和验收。
7. M7 汇总阶段性结果，避免把关键计量问题集中到项目末尾才发现。

已完成的 Protocol I 四轮核心与 Protocol III 三轮核心作为工程对照保留，不替代最终精确基线。

### 3.2 取消与暂不实施的内容

- M4 CipherGPT 原生实现、修复、mask 适配和性能实验取消。
- `ciphergpt_style_vfss_adapter` 不属于本轮任务。
- CipherGPT 不进入六种方案的正式性能比较。
- 历史 Direct Top-K 原型保留原身份，不直接改名为 BB90+DCF，也不自动新增为实施任务。
- CryptoMoE 保留为 M7 之后的独立工作负载方向。
- 不复用 M4 编号承载新任务。

取消任务不要求删除历史资料、旧分支或实验来源，也不改变参考目录的忽略和分发规则。

## 5. 新执行顺序

```text
M2 Protocol I 精确三轮核心
  → 实现与正确性验收
  → 通信测量及差异解释
  → 公共接口交接
  → M5 Protocol III 精确两轮核心
  → 实现与正确性验收
  → 通信测量及差异解释
  → 基础接口交接
  → M6A AAV86 两种升级实现
  → M6A 完整性能验收
  → M6B BB90+DCF 两种升级实现
  → M6B 完整性能验收
  → M7 六种方案统一报告
```

M3 是已完成前置基础，不重新安排实现。旧 M3→M4、M4→M5 阶段门取消。

### 5.1 核心轮数口径

- Protocol I：Theorem 4.1 的三轮核心。
- Protocol III：Theorem 4.2 的两轮核心。
- raw-score 输入、表示转换、逆映射和 mask 输出适配的实际轮数与成本另列。
- 主比较使用完整安全路径，不能只报告核心而遗漏适配。

Protocol I 沿用现有适配器时的七轮总路径仍是候选算式，不是既成实现。最终总轮数由真实消息依赖确定。

### 5.2 图升级轮数与证据边界

- Protocol I+AAV86 对应 CA compiler 的核心目标为 `2r+1`。
- Protocol III+AAV86 的 `2r` 是团队组合目标，必须独立论证和验证。
- BB90+DCF 两种组合按完整消息依赖推导轮数，不直接套用 AAV86 公式。
- 组合方案初始按项目扩展或待验证候选记录，满足相关条件后才能升级证据身份。

## 6. 基础协议阶段门

M2、M5 均执行：

```text
G1：实现与正确性完成
  → G2：通信核验及差异解释完成
  → G3：接口与证据交接完成
```

### 6.1 G1：实现门

必须提供：

- 适配器 conformance；
- 与冻结 oracle 的差分；
- 独立进程 E2E；
- 输入、输出及材料契约；
- 允许公开值和 Dealer 行为说明；
- 核心及端到端消息依赖审计。

论文精确身份还要求对应论文前提成立。不能只凭输出正确或轮数相同宣称精确复现。

### 6.2 G2：通信门

每次核验形成：

```text
论文成本公式
  ↔ 实际参数与消息下的实现成本
  ↔ 独立进程执行的实际发送量
```

Protocol I 主要对照 Theorem 4.1。Protocol III 主要对照 Theorem 4.2，并注明脚注中的共用掩码优化是否采用。

核验必须明确：

- sorting、单个 order statistic 与 Top-K mask 的功能区别；
- n、logical/padded 规模、位宽、rank 域和 payload；
- 核心、输入适配、输出适配与封装成本；
- total/per-party、发送/接收和单位转换；
- 随参数增长的实际趋势；
- 理论、历史和当前实测的区别。

total 只累加在线方发送量，received 用于核验，不重复计入。

通过条件是计数可信、对应关系明确、关键差异有解释，不要求 wire bytes 与理论 bit 数逐位相等。

数量级相符不能单独证明论文、代码或安全性正确；数量级不符时，应先定位参数、实现和计量差异，不能直接判定论文错误。

### 6.3 G3：交接门

交付物至少包括：

- 冻结 revision、标签和构建配置；
- 接口、输入输出、layout 和错误语义；
- 材料生成、绑定、分发及一次性消费规则；
- transport、session 和阶段边界；
- 分阶段计量说明；
- 正确性、轮数、安全与通信核验报告；
- 最小调用示例和复跑命令；
- 已知限制及不可直接复用的假设；
- 接收方复跑结果。

M2 由角色 A 交付、角色 B 接收。M5 由角色 B 交付、角色 A 交叉复跑，双方共同冻结进入 M6A 的基础接口。

代码可以分批合并，但“已合并”不等于 G2/G3 已通过。

## 7. 升级阶段门

### 7.1 M6A：AAV86

前置条件为 M2、M5 的实现、通信核验及交接完成。

M6A 必须完成：

1. 算法来源、CA 转换和稳定同分设计。
2. 自适应比较图、材料生成与 Dealer 在线静默方案。
3. Protocol I+AAV86 实现。
4. Protocol III+AAV86 实现。
5. 两种组合各自的正确性、泄露和消息审计。
6. 可信计量能力。
7. 统一矩阵及 `r=2..5` 的完整性能验收。
8. 报告、失败配置记录和接口交接。

完整图预留不能冒充已解决自适应 exact-edge 预处理。在线 Dealer 原型和明文图 oracle 不能当作目标安全协议。

### 7.2 M6B：BB90+DCF

M6A 完整性能验收完成后，M6B 才进入依赖实现和正式实验。

必须完成：

1. BB90 版本、适用范围、参数及概率保证说明。
2. 稳定第 K 大阈值与项目 rank 的映射。
3. 在线阈值与 DCF 预处理的安全衔接。
4. Protocol I+BB90+DCF 完整实现。
5. Protocol III+BB90+DCF 完整实现。
6. 正确性、泄露、材料和轮数审计。
7. 全部适用性能指标与统一矩阵记录。
8. 选择、DCF、适配及总路径的分阶段报告。

“投票”表示每个位置的秘密共享成员指示。必须保持同分按原始下标的规则，最终恰选 K 个位置。

仅得到第 K 大 score，或仅以 `score >= 阈值` 处理重复值，不算完成统一 Top-K 协议。

### 7.3 完整性能验收含义

M6A、M6B 分别对两种实现进行完整性能验收，不仅验证算法可运行。

保留项目总纲中的：

- 全部 `(n,K)` 配置；
- AAV86 `r=2..5`；
- 单独定义的 BB90 参数；
- LAN/WAN；
- 预热一次、正式五次；
- median/min/max；
- 离线时间与材料；
- 在线时间及 total/per-party/分方通信；
- 因果轮数、PRG、比较边和总时间；
- 完整 provenance。

成功运行配置的全部适用指标应齐全。无法承受的大规模点记录资源或失败原因，不外推填表，也不宣称该点成功。

平台性计量缺口不能用 `NOT_MEASURED` 掩盖后宣称“全部指标完成”。

## 9. 并行与合并规则

### 9.1 允许提前开展

- 论文与算法来源核对；
- 域、编码、消息和接口设计；
- 明文算法 oracle；
- 失败用例和独立 conformance；
- 实验矩阵、模板与报告设计。

### 9.2 不允许绕过

- 未完成 M2 交接就将依赖接口的 M5 实现标为验收完成；
- 未完成两次通信核验就用候选作为已核验精确基线；
- 未完成 M6A 完整性能验收就推进 M6B 的依赖实现和正式实验；
- 用代码合并、文档完成或字段存在替代阶段证据；
- 将分支进度写成 main 已完成。

每个 PR 处理一个明确实现步骤或治理变更。设计可以提前合并，依赖 runtime 的合并与验收遵循新顺序。
