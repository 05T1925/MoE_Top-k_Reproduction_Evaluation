## 3. 实际执行、正确性与性能缺口

隔离源码从零配置并构建 WSL Ubuntu 24.04.4 的 Release/EMP-ON 目标，命令和二进制 SHA-256 在仓库外 `e19_commands_and_binary_hashes.txt`，配置/构建日志同目录。AAV86 metrics/conformance 可执行文件在 `prlimit --as=3221225472` 下实际打印 16 行 `E16_PREFLIGHT_REJECTED ... reason=HARD_CAP_D_GT_256`，执行到容量检查而**未生成 key**。独立 Python `e19_resource_matrix.py` 用 checked uint64 复算 16 行，逐行与新 C++ `D/slots/P` 和真实拒绝原因断言一致，输出 16 行 CSV（PASS）。这是对固定门后真实包长和内存/磁盘的审查，不是通过移除门后运行的材料试验；物理资源与接收器长度上限使该试验不获准。

再次以 `/usr/bin/time -v` 运行**整个**容量/预检测试进程，elapsed `0:00.01`、最大 RSS `4,352 KiB`、exit 0，原件 `e19_preflight_timed.stdout/.stderr`。这只测到轻量预检程序的峰值，不能分配给任一 n/r，也绝非 T/P/keygen 或完整协议实际峰值；表中的逐档峰值仍为 `NOT_MEASURED`。

EMP-ON 全对全基线入口分别以 n1000/10000/100000/1000000、K80 实际调用，四次均 exit 1，原件含 `E16 baseline benchmark shape`。该入口只允许 n128/256、K2/8；此外现有基线收包 64 MiB 上限也低于 n1000 的固定布局材料量。基线没有同规模完整运行或配对测量，不能把 E17 的较小规模中位数移来比较。
